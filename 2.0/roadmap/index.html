    Roadmap¶

    This page lists what version 2 delivers, what is experimental, the limits you meet today and what is planned. Nothing under "Planned" exists, and none of it has a date.

    Delivered in version 2¶

    • Start Here, what's new in v2 and migrating to v2
    • One interpreter, written in Rust, behind the kgpy and kg commands (What Runs Where)
    • Language Additions, including modules; strict mode and lint
    • Errors with positions and kinds and the REPL
    • Compiling Klong to C for the static profile, a subset of the language. It has run with desktop C compilers and, for three examples, on two Raspberry Pi Picos
    • The conformance suite
    • The interpreter for boards and its tools (Native Runtime): building, the serial console, IPC and timers, the management node and porting to a board
    • kdb+ IPC and timers
    • Contributing

    Experimental¶

    • FPGA kernels: Klong functions compiled to hardware. The U250 runs the moving average, FIR filter and a 32-lane strategy replay.
    • The interpreter on boards: it passes the conformance suite on a desktop and has run the console suite on one ESP32-P4 board (ESP32-P4). Two Raspberry Pi Picos have run it with IPC between them (two Picos calling each other). The status table has the detail.

    Known limits¶

    Language¶

    Known bugs, where KlongPy's answer is wrong and the right one is known, are listed once, in Differences from Klong. The same page lists the limits of integer power on lists.

    Known limit: a Klong function that calls itself is bounded by the stack of the thread that runs it. Under kgpy, f::{:[x;f(x-1);0]};f(6000) runs and f(8000) gives range error: expression nested too deeply. Under kg the bound is 512 nested evaluations, so f(254) runs and f(255) gives that error; see the section on the interpreter on boards below.

    PyTorch backend¶

    Details are in PyTorch Backend and Autograd.

    • Floats are float32 on every device, so results differ from the numpy backend in the last digits.
    • A tensor cannot hold :undefined, so an :undefined inside a list differs from the numpy backend.
    • MPS has no float64.
    • .gradcheck needs the CPU device and raises on MPS.
    • .export does not complete for some Klong functions, those that branch on a tensor's value; check the export_error entry of its result.

    The interpreter on boards and under kg¶

    • Recursion depth on small stacks. The interpreter bounds the depth of nested evaluation and the stack it uses, and reports a range error when either is exceeded. kg allows 512 nested evaluations (--max-depth changes it): f::{:[x;f(x-1);0]};f(240) runs and f(255) gives a range error. The two RP2040 Picos had a 112 KiB stack on RC1. In the board test f::{:[x;1+f(x-1);0]}, both returned 113 for f(113) and a range error for f(114). RP2040 measurements
    • Heap needed to load large libraries. A load reads one statement at a time and keeps functions as their text. On the 64-bit host the management library (.l("mgmt")) needs a heap of about 43 KiB to load; .l("nstat") peaks at about 322 KB. On the RC1 serving Pico, the largest contiguous integer vector measured 6,826 elements after boot and 5,060 after a management call followed by two seconds idle. RP2040 memory measurements
    • IPC on a device has run only on two Picos. IPC between nodes and management-library calls have run on two Raspberry Pi Picos. The ESP32-P4 has run the console conformance suite only (the firmware has no IPC). The host build is tested against an open-source q implementation (PeachQ).
    • One flaky Rust test. data_nesting_is_bounded in native/klong-core/tests/full.rs fails in about one run in ten on a desktop. The cause is not known.
    • The default build of kg does not declare the conformance tags bigint, timers, ipc or desktop, so the suite does not test those areas for it.

    Interop¶

    • IPC has been tested against PeachQ, not against kdb+. The tests that use PeachQ are opt-in (see Contributing).

    Planned¶

    None of the following exists.

    • A WebAssembly build of the emitted C. The C emitter produces freestanding C99; compiling that to WebAssembly is not built. The WebAssembly import module name of an extern is reserved for it (see Compiling Klong to C).
    • Testing against real kdb+. The IPC code would be run against a kdb+ server and client, which has not been done.
    • CI for the Rust tiers. The GitHub workflows run the Python tests, a linter and the docs build. They do not run the Rust workspace tests or conformance/run.py against the kg binary. See Contributing.
